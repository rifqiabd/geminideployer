Peta Migrasi Teknis

Pemisahan Frontend & Backend
pada gemini-deployer

Rencana bertahap memecah Worker monolitik (Hono + SSR + KV/D1/R2) menjadi lapisan API dan lapisan antarmuka yang terpisah, lengkap dengan pemetaan setiap endpoint, urutan pengerjaan, serta bagian yang sebaiknya tidak disentuh.

Versi 1 · 22 September 2026 Basis: 21 rute terdaftar Stack: Workers, Hono, KV, D1, R2 Status: belum ada perubahan kode

01 Ringkasan Eksekutif

Kesimpulan lebih dulu, detail menyusul.

Aplikasi ini sudah setengah terpisah

Semua interaksi dinamis sudah lewat /api/* berformat JSON, dan aset statis sudah disajikan dari public/. Yang belum terpisah hanyalah rendering halaman, yang masih dirakit di server sebagai string HTML. Jadi pekerjaan ini bukan "membangun API dari nol", melainkan memindahkan lapisan tampilan.

Pemisahan penuh lintas domain berbiaya tinggi

Memindahkan frontend ke Cloudflare Pages atau domain lain menuntut rombak autentikasi (cookie statis tidak sah lintas situs) plus penulisan ulang sekitar 3.500 baris generator HTML menjadi komponen. Manfaatnya kecil dibanding risikonya pada aplikasi yang nilai utamanya justru ada di halaman cetak dan laporan guru.

Rekomendasi

Tempuh jalur bertahap: bekukan kontrak API lebih dulu, pisahkan panel admin (dashboard, editor, rekap, media, koreksi esai) menjadi SPA yang memanggil API, lalu biarkan halaman siswa dan lembar cetak tetap SSR. Pemisahan domain penuh ditunda sampai ada kebutuhan deploy/CDN yang nyata.

Skenario A — same-origin

SPA disajikan Worker yang sama. Tanpa CORS, tanpa ubah cookie, URL tetap /p/.... disarankan

Skenario B — cross-origin

Frontend di Pages/domain lain, API di Worker. Perlu token/header auth & CORS ketat. tunda

Yang tak berubah

Lapisan data tetap di backend: KV STORAGE, D1 DB, R2 opsional, dan proxy generate gambar.

02 Arsitektur Saat Ini

Satu Worker melayani HTML, JSON, dan biner sekaligus.

Berkas src/index.ts membuat instance Hono, memasang middleware auth, lalu mendaftarkan rute dari modul-modul terpisah: registerMediaRoutes, registerQuizEditorRoutes, registerEssayGradingRoutes, registerGuideRoute. Konfigurasi wrangler.jsonc memakai assets binding ./public sehingga apa pun di public/ ikut disajikan sebagai berkas statis.

# Batas yang sudah ada hari ini

  Browser
    │
    ├── /p/:slug, /, /p/:slug/data   ← SSR: HTML dirakit di server
    │        (quiz-page.ts, quiz-report.ts, quiz-editor.ts, quiz-essay.ts, guide.ts)
    │
    ├── /api/*                          ← sudah JSON
    │        (login, deploy, delete, submit, quiz/save, quiz/essay, media/*)
    │
    └── /media/:slug/:name               ← biner dari R2 atau KV

  Data layer (tetap di backend)
    KV STORAGE  ·  D1 DB  ·  R2 MEDIA (opsional)  ·  proxy IMGGEN
Temuan penting untuk keamanan

quiz-page.ts hanya menanam metadata kuis (slug, judul, KKM) ke konfigurasi klien. Kunci jawaban dan pembahasan tidak pernah dikirim ke browser — penilaian dilakukan di server dari spesifikasi di KV. Artinya memindahkan tampilan ke klien tidak melemahkan anti-kecurangan, asalkan endpoint baru juga tidak mengekspor kunci.

Koreksi (28 Sep 2026): klaim lama bahwa parameter ?kunci=1 “tidak punya auth check” sudah tidak berlaku. Sejak hardening auth (docs/plan-hardening-auth.md T6), GET /p/<slug>?print=1&kunci=1 tanpa sesi admin valid dijawab 404 di server; ?print=1 tanpa kunci tetap publik. Endpoint baru hasil migrasi SPA wajib meniru gerbang ini dan tidak boleh mengekspor kunci jawaban ke klien.

04 Pilihan Arsitektur A vs B

Dua bentuk pemisahan, dengan konsekuensi yang sangat berbeda.

Skenario A — Frontend SPA, Worker yang sama

same-origin · risiko rendah
  • Worker menyajikan aset SPA dan /api/*.
  • URL tetap /p/... — tautan guru tidak rusak.
  • Cookie SameSite=Lax tetap sah, tidak ada CORS.
  • Struktur kode terpisah tanpa biaya operasional tambahan.

Skenario B — Frontend di Pages/domain lain

cross-origin · risiko tinggi
  • Perlu CORS dengan kredensial + origin eksplisit (bukan *).
  • Cookie lintas situs butuh SameSite=None; Secure, atau ganti ke token.
  • Cookie sesi sekarang berupa string statis — tidak layak jadi bearer token.
  • Menambah titik gagal: dua deploy, dua pipeline, dua set environment.

Matriks keputusan

AspekSkenario ASkenario B
Perubahan authTidak adaRombak (CORS + cookie/token)
Deploy terpisahTidakYa — Pages + Worker
Risiko regresiSedangTinggi
Manfaat utamaKode lebih rapi, iterasi lebih cepatSkala/CDN terpisah
Cocok untukSekolah & tim kecilMulti-tenant besar

Rujuk docs/analisis-resource.html untuk konteks model distribusi: bila arahnya multi-sekolah, Skenario B baru punya alasan kuat.

05 Auth Lintas-Origin

Bagian yang paling mudah diremehkan.

Saat ini src/auth.ts memakai konstanta AUTH_SESSION = 'authenticated_user' sebagai nilai cookie — cookie httpOnly, Secure, SameSite=Lax. Selama semuanya satu origin (Skenario A), skema ini tetap bekerja apa adanya. Yang berubah hanya bila frontend pindah domain.

// Skema cookie sekarang (sederhana, cukup untuk same-origin)
auth_session=authenticated_user; HttpOnly; Secure; SameSite=Lax

// Bila cross-origin: Lax tidak akan terkirim pada permintaan lintas situs.
// Dua jalan keluar:
//   1) SameSite=None; Secure  +  CORS credentials: true, origin eksplisit
//   2) Ganti ke token bertanda tangan di header Authorization (disarankan)
Jangan gabungkan cookie statis dengan model tenant

Nilai cookie yang bisa dipalsukan adalah kelemahan yang sudah tercatat di docs/analisis-resource.html. Sebelum beralih ke Skenario B, perbaiki dulu sesi bertanda tangan; CORS saja tidak memperbaiki kelemahan ini.

Kerangka CORS yang diperlukan untuk Skenario B:

// Origin harus eksplisit; "*" dilarang saat memakai kredensial
Access-Control-Allow-Origin: https://<domain-frontend>
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization

06 Alur yang Tidak Boleh Dipindah

Memindahkan ini ke klien justru merusak fungsinya.

Lembar cetak

renderPrintSheet menghasilkan dokumen HTML yang tujuannya dicetak, bukan dioperasikan. SPA menambah kompleksitas tanpa manfaat apa pun di sini.

Penilaian jawaban

quiz-grade.ts mengevaluasi jawaban di server. Skor dan kunci tidak boleh melewati batas browser.

Penandaan media

Token media:<slot> diselesaikan di server menjadi /media/... dan perlu tahu slot mana yang benar-benar ada. Logika ini tetap di backend.

Catatan pada komponen yang sudah interaktif

  • public/vendor/quiz-editor.js sudah berkomunikasi ke /api/quiz/:slug/save — bagian ini paling siap dipindah.
  • public/vendor/quiz-essay.js sudah memanggil /api/quiz/:slug/essay.
  • Panel media masih memuat skrip inline yang langsung memanggil /api/media/* (unggah, hapus, generate, gen-config) — perlu diekstrak menjadi modul sebelum jadi SPA.
  • Halaman siswa (quiz-page.ts) sudah punya skrip klien sendiri untuk pengiriman jawaban — tidak perlu diubah.

07 Roadmap Bertahap

Tiap fase berdiri sendiri; berhenti kapan saja tanpa meninggalkan sistem setengah jadi.

Fase 0

Bekukan kontrak API

tanpa ubah perilaku
  • Dokumentasikan bentuk respons tiap /api/* yang sudah ada. 0,5 hari
  • Samakan format galat (satu bentuk JSON untuk semua kegagalan). 0,5 hari
  • Petakan setiap pemanggilan fetch() di public/vendor/* ke rutenya. 0,5 hari
Hasil: batas API terdokumentasi, tidak ada kode perilaku yang berubah.
Fase 1

Siapkan kerangka frontend (Skenario A)

rendah
  • Tambahkan shell SPA di public/ yang menyajikan panel admin. 0,5 hari
  • Ekstrak skrip inline panel media menjadi modul di public/vendor/. 1 hari
  • Tambahkan tiga endpoint JSON di bagian 3.3. 1 hari
Hasil: semua data admin sudah bisa diambil sebagai JSON, halaman lama masih jalan.
Fase 2

Pindahkan panel admin ke SPA

pekerjaan utama
  • Editor soal: port quiz-editor.ts ke komponen. Mulai dari sini karena paling siap. 2–3 hari
  • Dashboard: daftar kuis, statistik media, aksi deploy/hapus. 1–2 hari
  • Rekap data: tabel nilai + analisis butir, dengan paginasi. 2 hari
  • Panel media & koreksi esai. 2 hari
  • Arahkan ulang rute SSR admin lama ke shell SPA. 0,5 hari
Hasil: dashboard, editor, rekap, media, dan esai dilayani satu SPA.
Fase 3

Putuskan nasib halaman siswa & cetak

disarankan: biarkan SSR
  • Uji ulang alur siswa dan cetak pasca-Fase 2 (jangan ada regresi). 1 hari
  • Bila tetap SSR: tandai jelas sebagai lapisan terpisah di kode. 0,5 hari
  • Bila ingin dijadikan SPA: perkirakan 4–6 hari ekstra, manfaat kecil.
Hasil: batas frontend/backend final dan terdokumentasi.
Fase 4

Opsional: pindah ke domain terpisah (Skenario B)

hanya bila perlu
  • Perbaiki sesi menjadi bertanda tangan lebih dulu. 1–2 hari
  • Pasang CORS dengan origin eksplisit + kredensial. 0,5 hari
  • Pindahkan aset SPA ke Pages, atur dua pipeline deploy. 1 hari
  • Uji ulang seluruh alur lintas-origin, termasuk unggah media. 1 hari
Hasil: frontend dan backend benar-benar terdeploy terpisah.
Perkiraan total

Fase 0–3 (Skenario A, siswa & cetak tetap SSR): sekitar 12–17 hari kerja. Menambah Fase 4: sekitar 4–6 hari lagi. Memaksa siswa & cetak jadi SPA menambah 4–6 hari dengan manfaat paling tipis.

08 Risiko & Regresi

Bagian yang paling mungkin rusak saat render dipindah.

RisikoPemicuDampakMitigasi

Navigasi kuis longsor Urutan soal & pengacakan dari seededOrder Siswa dapat urutan berbeda Jangan pindahkan logika pengacakan ke klien
Cetak berantakan CSS khusus print di halaman siswa Lembar ujian tidak layak cetak Biarkan SSR; uji cetak setiap fase
Sesi hilang lintas-origin Cookie SameSite=Lax Guru terkunci di luar Hanya berlaku di Skenario B; perbaiki auth lebih dulu
Unggah media gagal Multipart + CORS preflight Gambar tidak masuk Uji unggah lintas-origin secara khusus, termasuk batas ukuran
Rekap lambat Analisis butir dihitung ulang tiap permintaan SPA terasa berat Paginasi + pertimbangkan cache hasil analisis
Rahasia bocor Terbawa ke bundel depan Kunci IMGGEN terekspos Semua panggilan pihak ketiga tetap di Worker

10 Rekomendasi

Bila hanya boleh menempuh satu jalan, ambil ini.

1 Skenario A, bukan B

Pisahkan lapisan di dalam Worker yang sama. Dapat sebagian besar manfaat tanpa mengorbankan keamanan sesi atau kestabilan deploy.

2 Admin dulu, siswa belakangan

Panel admin sudah interaktif dan pemakainya sedikit. Halaman siswa justru paling sensitif dan paling diuntungkan oleh kecepatan SSR.

3 Perbaiki auth sebelum domain terpisah

Sesi statis adalah utang yang harus dibayar sebelum menambah permukaan baru dari CORS.

Keputusan yang masih terbuka

PertanyaanMengapa penting
Apakah frontend memang perlu domain/CDN sendiri? Tanpa jawaban "ya", Skenario B tidak punya alasan sama sekali.
Kerangka SPA: React, Vue, atau tetap vanilla? Menentukan besar pekerjaan porting dan apakah perlu langkah build.
Apakah public/vendor/* yang ada mau dipertahankan? Bila ya, migrasi bisa dilakukan bertahap, komponen demi komponen.
Apakah rekap nilai perlu paginasi server? Menentukan bentuk endpoint laporan sebelum SPA ditulis.
