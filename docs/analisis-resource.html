Analisis Teknis

Kesiapan Repo untuk Banyak Sekolah,
Banyak Siswa & Guru

Penilaian menyeluruh atas gemini-deployer (Cloudflare Workers + Hono + KV + D1 + R2) untuk dipakai lintas beberapa sekolah sekaligus, beserta roadmap bertahap menuju model distribusi hybrid dengan pendaftaran mandiri.

Versi 2.1 · diperbarui 30 Sep 2026 Model: Hybrid + Self-service Stack: Workers, KV, D1, R2 Status kode: single-tenant (Tahap 0 hampir tuntas)

01 Ringkasan Eksekutif

Produk intinya sudah kuat: penilaian dihitung di server, ada editor soal, analisis butir soal, dan koreksi esai manual. Yang belum ada adalah lapisan tenant & identitas.

#TemuanDampakPrioritas
1 Sesi login = cookie statis berisi string literal authenticated_user RESOLVED (28 Sep 2026): sesi HMAC-SHA256 bertanda tangan, punya exp; cookie literal lama ditolak Akses admin bisa dipalsukan siapa pun yang tahu nilainya Selesai
2 Password admin hardcoded admin123 dan tidak dibaca dari env RESOLVED (28 Sep 2026): dibaca dari APP_PASSWORD dan wajib; fallback dihapus Semua sekolah berbagi satu kredensial Selesai
3 Stored XSS di halaman rekap (payload_json + user_id tanpa escape) RESOLVED: escapeHtml() dipakai pada created_at, user_id, summary, dan JSON.stringify(payload) Siswa bisa menjalankan skrip di browser guru Selesai
4 Slug global dari judul → tabrakan antar guru/sekolah Data kuis bisa tertimpa tanpa peringatan Tinggi
5 Query D1 tanpa LIMIT, analitik dihitung ulang tiap request Lambat + mahal begitu ada ribuan kiriman Tinggi
6 Indeks aplikasi dibaca dari KV list + get() berurutan Dashboard O(N), mentok ~1000 key, kena konsistensi eventual Tinggi
7 Identitas siswa dari input bebas, tanpa kelas/daftar hadir Tidak bisa cegah spam/peniruan, tidak bisa rekap per kelas Tinggi
8 Tidak ada tenant & tidak ada pendaftaran mandiri Sekolah tidak bisa melayani dirinya sendiri Tinggi
9 Media jatuh ke KV kalau R2 tidak dipasang KV bukan tempat binary: mahal & cepat habis kuota Sedang
10 /api/save/:slug terbuka (CORS global, tanpa rate limit) Bisa dibanjiri untuk membakar kuota D1 Sedang
11 Edit soal tanpa versi (last-write-wins) + KV eventual Dua guru bisa saling menimpa; siswa lihat versi basi Sedang
Catatan penting soal berbagi ke banyak sekolah

Begitu tautan disebar, setiap celah keamanan di atas menjadi celah milik semua orang sekaligus. Satu siswa yang menemukan cara memalsukan sesi bisa masuk ke dashboard seluruh sekolah di instance publik. Karena itu Tahap 0 pada roadmap bersifat wajib sebelum promosi apa pun dilakukan.

Tiga hal yang paling mendesak

1 Sesi yang bisa dipalsukan

Ini akar kepercayaan sistem. Selama cookie bisa dibuat sendiri oleh pengguna, semua kontrol akses di atasnya tidak berarti.

2 XSS di halaman rekap

Guru adalah pengguna paling berharga, dan saat ini justru bisa diserang lewat input siswa.

3 Indeks D1 + LIMIT

Kunci performa sekaligus biaya. Tanpa ini, biaya naik seiring bertambahnya data, bukan seiring pemakaian.

03 Analisis Per Dimensi

Enam area yang menentukan apakah repo ini bisa melayani banyak sekolah dengan aman.

3.1  Tenant & Autentikasi Sebagian selesai

Diperbarui 30 Sep 2026

Dua butir pertama di bawah sudah selesai lewat docs/plan-hardening-auth.md (28 Sep 2026) dan ditandai dengan coretan. Yang masih berlaku: isolasi data dan kesatuan sumber kebenaran auth sudah beres, tapi tenant tetap belum ada.

  • APP_PASSWORD = 'admin123' masih berupa konstanta di src/index.ts dan tidak dibaca dari env — SELESAI. Password dibaca dari APP_PASSWORD; bersama SESSION_SECRET keduanya wajib, dan kalau kosong login menjawab 503 berisi instruksi setup.
  • isAuthed() di src/auth.ts hanya membandingkan cookie dengan konstanta authenticated_user. — SELESAI. Sesi kini HMAC-SHA256 bertanda tangan (signSession/verifySession) dengan exp; cookie literal lama ditolak. Catatan httpOnly di butir lama tetap benar sebagai pelajaran: atribut itu menghalangi JavaScript membaca cookie, bukan membuat-nya.
  • Belum ada school_id di key KV maupun di tabel D1, sehingga tidak ada isolasi data sama sekali. Di Lintasan A, satu query yang lupa difilter langsung berarti kebocoran data antar sekolah. (Masih terbuka.)
  • Ada dua sumber kebenaran untuk autentikasi: sebagian rute memakai cek cookie langsung di src/index.ts, sebagian lain memakai isAuthed(). — SELESAI. Semua route admin lewat getSession()/requireAdmin/guard per modul; tidak ada lagi pembacaan cookie mentah.

Arah perbaikan

// src/auth.ts — sesi bertanda tangan, satu middleware untuk semua rute
export type Session = { userId: string; schoolId: string; role: 'guru' | 'admin_sekolah' };

export async function readSession(c, secret) {
  const token = getCookie(c, 'session');
  if (!token) return null;
  const [body, sig] = token.split('.');
  if (!timingSafeEqual(sig, await hmac(secret, body))) return null;   // tanda tangan
  const data = JSON.parse(atob(body));
  if (data.exp < Date.now()) return null;                            // masa berlaku
  return data;
}

Password diambil dari npx wrangler secret put APP_PASSWORD, dan seluruh cek akses dialihkan ke satu middleware yang juga mengisi schoolId ke konteks request.

3.2  Model Data (D1) Tinggi

Seluruh sistem saat ini berdiri di atas satu tabel:

-- schema.sql (saat ini)
CREATE TABLE app_records (
  id TEXT PRIMARY KEY,
  app_slug TEXT NOT NULL,
  user_id TEXT,
  payload_json TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_records_slug ON app_records(app_slug);
  • Tidak ada school_id, class_id, assessment_id yang nyata, attempt_no, maupun status percobaan.
  • Jawaban per soal menumpuk di dalam blob payload_json, sehingga analitik lintas kelas atau lintas sekolah mustahil tanpa membaca dan mengurai seluruh blob.
  • Query rekap di src/index.ts dan src/quiz-essay.ts tidak memakai LIMIT, padahal setiap baris di-JSON.parse di memori Worker.
  • Analisis butir soal (src/quiz-report.ts) dihitung ulang setiap halaman dibuka dengan biaya O(seluruh kiriman). Semakin lama dipakai, semakin berat — inilah yang membuat biaya tumbuh mengikuti jumlah data, bukan jumlah pemakaian.

Arah perbaikan

-- skema multi-tenant (ringkas)
CREATE TABLE schools  (id TEXT PRIMARY KEY, name TEXT, plan TEXT, created_at …);
CREATE TABLE users    (id TEXT PRIMARY KEY, school_id TEXT, email TEXT UNIQUE,
                       role TEXT, password_hash TEXT, …);
CREATE TABLE classes  (id TEXT PRIMARY KEY, school_id TEXT, teacher_id TEXT, name TEXT);
CREATE TABLE students (id TEXT PRIMARY KEY, school_id TEXT, class_id TEXT, name TEXT);
CREATE TABLE assessments (id TEXT PRIMARY KEY, school_id TEXT, class_id TEXT,
                          title TEXT, slug TEXT, created_at …);
CREATE TABLE attempts (id TEXT PRIMARY KEY, school_id TEXT, assessment_id TEXT,
                       student_id TEXT, attempt_no INT, score REAL, lulus INT,
                       submitted_at …);
CREATE TABLE attempt_answers (attempt_id TEXT, question_id TEXT, answers_json TEXT, …);
-- catatan: setiap query WAJIB disaring school_id dari sesi

3.3  Penamaan & Penyimpanan Konten (KV) Tinggi

  • sanitizeSlug(title) menghasilkan namespace slug yang global. Dua guru di sekolah berbeda dengan judul sama akan saling menimpa html:, meta:, quiz:, dan quizsource:. Yang paling berbahaya adalah quizsource: — ia adalah sumber kebenaran editor soal, jadi soal yang sudah diperbaiki bisa hilang tanpa peringatan.
  • Dashboard membaca seluruh daftar aplikasi lewat STORAGE.list({ prefix: 'meta:' }), lalu get() satu per satu ditambah withMediaStats() yang melakukan list/get lagi. Ini pola N+1 operasi KV.
  • Editor soal menyimpan ke KV tanpa penanda versi. Dua guru yang mengedit bersamaan membuat yang terakhir menulis menang, dan karena KV bersifat eventual, siswa bisa melihat HTML lama sampai propagasi selesai.
Pelajaran praktis

KV sangat cepat untuk dibaca dengan kunci yang sudah diketahui, tetapi buruk sebagai daftar/indeks. Pindahkan daftar aplikasi ke D1 (satu query + pagination), dan biarkan KV tetap menjadi tempat konten per kunci.

3.4  Identitas Siswa Tinggi

Identitas siswa diambil apa adanya dari body request: userId = body.user || body.name || body.student_name || 'anonim' (src/index.ts), dan form siswa (src/quiz-page.ts) memang meminta nama bebas dengan placeholder "Tulis nama lengkap dan kelas...".

  • Satu nama bisa dikirim berkali-kali tanpa pembatasan.
  • Siswa bisa mengaku sebagai nama temannya.
  • Dua siswa bernama sama tidak dapat dibedakan di rekap.
  • Kelas tidak pernah tercatat sebagai data, sehingga guru tidak bisa membandingkan hasil antar kelas.

Untuk konteks sekolah, yang dibutuhkan bukan login siswa penuh, melainkan kode kelas ditambah pemilihan nama dari daftar hadir yang diunggah guru, lalu pencatatan attempt_no untuk mengatur berapa kali percobaan diizinkan.

3.5  Keamanan

a. Sesi dapat dipalsukan Kritis

Lihat 3.1. Tidak ada tanda tangan, tidak ada masa berlaku yang mengikat ke pengguna tertentu.

b. Stored XSS di halaman rekap Kritis

Tabel rekap menempelkan JSON.stringify(payload, null, 2) dan user_id mentah ke dalam HTML. Nama siswa bebas teks, dan jawaban esai juga. Akibatnya siswa dapat menanam <script> yang berjalan di browser guru saat membuka Log Data. Helper escapeHtml() sudah tersedia di repo, jadi yang kurang hanya penerapan yang konsisten.

c. Endpoint publik tanpa proteksi Sedang

/api/save/:slug memakai cors() global dan tidak memiliki rate limit atau captcha. Penilaian memang aman karena dihitung di server, tetapi tabel D1 bisa dibanjiri permintaan.

d. Yang sudah baik dan perlu dipertahankan Bagus

  • Penilaian dan perhitungan skor dilakukan di server, tidak bisa dipalsukan dari browser.
  • Tipe file unggahan ditentukan dari magic bytes, bukan dari Content-Type kiriman browser.
  • SVG ditolak (mencegah XSS lewat SVG yang disajikan dari domain yang sama).
  • Ada batas ukuran file dan konversi WebP di sisi perangkat guru untuk menghemat kuota.
  • Rate limit generate AI (6 gambar/menit) dengan pola KV counter — pola ini bisa dipakai ulang untuk /api/save dan pendaftaran sekolah.

3.6  Media Sedang

  • putMedia otomatis jatuh ke KV bila binding R2 tidak dipasang. Untuk satu sekolah ini masih berjalan; untuk banyak sekolah, ini jalur biaya yang paling cepat membengkak. KV bukan penyimpanan binary: batas nilai sekitar 25 MiB, ditagih per operasi, dan ada batas 1 tulis per detik per kunci.
  • Konversi WebP dan pengecilan di perangkat guru sudah tepat dan menghemat kuota secara signifikan. Pertahankan, lalu tambahkan varian ukuran (thumbnail) untuk sekolah dengan koneksi lemah.
  • Kunci media <slug>/<nama> mewarisi masalah slug global yang sama: perlu diberi prefix school_id/assessment_id/slot.

04 Batasan Cloudflare

Patokan biaya & performa yang menentukan bentuk arsitektur. Verifikasi ulang angka ini di dokumentasi Cloudflare sebelum dipakai untuk keputusan anggaran.

LayananBatas yang perlu diperhatikanImplikasi
Workers (gratis) ~100k request/hari, CPU 10 ms per request Render rekap besar akan menabrak batas CPU; paket Paid (~$5/bln) praktis wajib begitu beberapa sekolah aktif
Workers (paid) CPU hingga 30 detik, kuota request jauh lebih besar Memberi ruang untuk rekap, tetapi tetap jangan O(seluruh histori)
KV ~1k tulis/hari & 100k baca/hari (gratis); value ~25 MiB; 1 tulis/detik/kunci Setiap kiriman siswa = tulis D1 + baca KV; media di KV cepat menghabiskan kuota
KV (konsistensi) Eventual — list dan get bisa telat beberapa detik Jangan memakai KV list sebagai indeks utama
D1 ~5 GB, ~5 juta baris dibaca/hari, ~100k baris ditulis/hari (gratis) Bottleneck ada di baris dibaca, karena rekap membaca semua baris
R2 Penyimpanan objek murah, tanpa biaya keluar Wajib untuk media pada skala banyak sekolah
Inti masalahnya

Bottleneck-nya bukan kapasitas penyimpanan, melainkan jumlah baris yang dibaca dan jumlah tulis KV. Keduanya berakar pada pola akses data saat ini, bukan pada pilihan layanan.

05 Model Distribusi: Hybrid + Pendaftaran Mandiri

Repo ini akan dipakai dua arah sekaligus, dengan satu basis kode.

Lintasan A — Instance publik

Sekolah mendaftar sendiri · biaya ditanggung pengelola

  • Halaman depan publik + pendaftaran sekolah (nama, email admin, verifikasi, Turnstile).
  • Sekolah = tenant; admin sekolah mengundang guru lewat tautan undangan.
  • Siswa masuk memakai kode kelas, lalu memilih namanya dari daftar hadir.
  • Kuota per sekolah yang terlihat oleh guru (asesmen, kiriman/bulan, MB media, AI).
  • Panel super-admin: daftar sekolah, pemakaian, aktif/nonaktif, hapus data.
  • Tes isolasi tenant otomatis — penjaga paling penting di lintasan ini.

Lintasan B — Deploy sendiri

Sekolah punya akun & data sendiri · biaya ditanggung sekolah

  • Tombol Deploy to Cloudflare + wizard /setup saat pertama dibuka.
  • Wizard membuat admin sekolah pertama dan menyiapkan skema.
  • Berjalan penuh tanpa layanan pihak ketiga — tidak wajib email atau OAuth.
  • Dokumen "deploy dalam 5 menit" + checklist secret.
  • Panduan guru (docs/panduan-pakai.md) bisa dipakai apa adanya.

5.3  Satu basis kode, bukan dua

Kunci desainnya: bangun skema multi-tenant lebih dulu, lalu instance mandiri hanyalah deployment dengan satu tenant di dalamnya. Dengan begitu tidak ada dua basis kode yang harus dirawat paralel.

  • Tabel inti selalu membawa school_id.
  • Middleware tenant mengambil school_id dari sesi; di deployment mandiri nilainya selalu satu sekolah yang sama.
  • Tidak ada fitur yang "hanya ada di instance publik" kecuali pendaftaran publik, kuota, dan panel super-admin — dan itu dipasang sebagai lapisan opsional yang dimatikan di mode mandiri.

5.4  Konsekuensi hukum & operasional (khusus Lintasan A)

Bukan nasihat hukum

Di Lintasan A kamu menyimpan data anak-anak dari banyak sekolah. Ini daftar hal yang wajib dibahas bersama pihak yang paham regulasi sebelum dibuka ke publik.

Dasar & dokumen

  • Sekolah adalah pengendali data, kamu pemroses — siapkan perjanjian pemrosesan data ringkas yang disetujui saat pendaftaran.
  • Kebijakan privasi + syarat layanan, ditulis dengan bahasa sederhana untuk guru.

Minimisasi & retensi

  • Jangan meminta NISN, alamat, atau kategori data khusus. Nama + kelas sudah cukup.
  • Hapus otomatis setelah jangka waktu tertentu (mis. 12 bulan), dengan opsi lebih cepat.

Hak subjek data

  • Ekspor dan hapus data per siswa, per kelas, per sekolah — sebagai fitur, bukan permintaan manual.
  • Catatan pemrosesan dan prosedur notifikasi insiden (tenggat notifikasi diatur regulasi).

Operasional

  • Moderasi konten: mekanisme lapor & take-down untuk foto dan hasil AI, plus kebijakan konten.
  • Kanal dukungan (email/WhatsApp) + FAQ. Tanpa ini, jumlah sekolah akan tumbuh lebih cepat daripada kemampuan melayani.

5.5  Layanan pihak ketiga yang dibutuhkan

Dua kebutuhan yang paling cepat muncul, dengan opsi yang sudah ditelusuri lewat indeks layanan:

KebutuhanOpsi yang ditelusuriCatatan
Login & verifikasi guru/sekolah Magic Auth — magic link, berjalan di edge sehingga cocok untuk Workers Alternatif: sesi sendiri di D1 + kode OTP via email. Lebih murah dan lebih mudah dikontrol, tetapi kamu menanggung sendiri alur keamanannya.
Email transaksional (verifikasi, undangan, reset) Knock — orkestrasi notifikasi lewat REST, aman di edge Alternatif: AWS SES lebih murah pada volume besar, tetapi menuntut pengelolaan reputasi pengirim sendiri.

Pertimbangan tambahan untuk Fase lanjutan: login Google Workspace sekolah — banyak sekolah sudah memiliki akun @sekolah.sch.id, sehingga guru tidak perlu membuat kata sandi baru.

06 Roadmap

Tahap 0 dan 1 bersifat serial dan wajib. Setelah itu Lintasan B dan A boleh berjalan paralel — Lintasan B disarankan lebih dulu karena lebih cepat memberi manfaat dan risikonya jauh lebih kecil.

Tahap 0

Wajib sebelum disebar ke siapa pun

Prioritas tertinggi

Status 30 Sep 2026: tiga dari empat selesai.

  • Pindahkan kata sandi ke secret: npx wrangler secret put APP_PASSWORD, lalu baca dari env. — SELESAI 28 Sep 2026.
  • Ganti cookie statis dengan sesi bertanda tangan (HMAC/jose) berisi { userId, schoolId, role } + masa berlaku; satukan semua cek ke satu middleware. — SELESAI untuk sesi bertanda tangan dan penyatuan middleware (getSession()/requireAdmin). schoolId/role menyusul di Tahap 1 karena tenant belum ada.
  • Terapkan escapeHtml() pada seluruh keluaran admin, terutama tabel rekap dan detail payload. — SELESAI 28 Sep 2026 untuk halaman rekap; audit menyeluruh sisa title dashboard dan URL media kaya.
  • Rate limit per IP di /api/save/:slug, memakai pola KV counter yang sudah ada di fitur generate gambar. (Masih terbuka. Generate AI dan login sudah ber-rate-limit.)

Hasil: tidak ada celah yang ikut tersebar saat tautan mulai dibagikan.

Tahap 1

Fondasi bersama — satu basis kode

Serial
  • Skema multi-tenant: schools → users(role) → classes → students → assessments → attempts → attempt_answers, semua baris membawa school_id.
  • Middleware tenant: setiap query disaring school_id dari sesi — tidak boleh bergantung pada slug di URL.
  • Pisahkan identitas dan URL: UUID untuk kunci KV (quiz:<school>/<id>), slug hanya untuk alamat yang enak dibaca, dengan pemeriksaan keunikan sebelum simpan.
  • Pindahkan indeks aplikasi dari KV list ke tabel D1 dengan pagination. (Sebagian: readD1Slugs() di src/app-index.ts sudah jadi jalur darurat.)
  • Tambahkan LIMIT di semua query rekap; pindahkan perhitungan analitik butir soal ke saat submit (atau Queue → pembaruan terbatas) dan simpan hasilnya.
  • R2 untuk media dengan kunci school_id/assessment_id/slot. — R2 SUDAH AKTIF di production & staging. Sisa: kunci masih <slug>/<name>, belum ber-namespace tenant.

Hasil: deployment mandiri sudah aman dipakai satu sekolah — Lintasan B siap dirilis.

Tahap 2

Lintasan B rilis — deploy sendiri

Risiko rendah
  • Wizard /setup pertama kali: buat admin sekolah + siapkan skema.
  • Tombol Deploy to Cloudflare + dokumentasi "5 menit" + checklist secret.
  • Mode mandiri berjalan penuh tanpa layanan pihak ketiga.

Hasil: sekolah pilot bisa memakai dan memiliki datanya sendiri, tanpa kamu memikul data anak mereka.

Tahap 3

Lintasan A rilis — instance publik

Butuh keputusan hukum
  • Halaman depan publik + pendaftaran sekolah (verifikasi email + Turnstile).
  • Peran admin_sekolah / guru, undangan guru, kode kelas, daftar hadir siswa, pengaturan jumlah percobaan.
  • Kuota per sekolah + panel super-admin (daftar sekolah, pemakaian, aktif/nonaktif, hapus data).
  • Tes isolasi tenant yang dijalankan otomatis di CI.
  • Analitik pemakaian per sekolah sebagai dasar kuota (Analytics Engine + tabel counter).
  • Dokumen kepatuhan: kebijakan privasi, syarat layanan, perjanjian pemrosesan data, kebijakan konten, prosedur insiden.

Hasil: sekolah dapat melayani dirinya sendiri, dan kuota terlindungi dari penyalahgunaan satu pihak.

Tahap 4

Skala & kepatuhan berkelanjutan

  • Pagination di semua daftar; arsip rekap lama ke R2 (NDJSON) setelah periode retensi.
  • Tenant per subdomain (sekolah-a.domainmu.id) memakai custom hostname, school_id di-resolve dari hostname.
  • Varian ukuran gambar (thumbnail) + cache lebih agresif di tepi.
  • Self-service: ekspor & hapus data per siswa / kelas / sekolah.
  • Observability: Workers Logs + peringatan saat pemakaian mendekati batas.

Hasil: biaya tetap datar meski data terus tumbuh.

Risiko biaya terbesar

Di Lintasan A, risiko terbesar bukan pada software atau jumlah sekolah, melainkan pada satu sekolah yang menghabiskan kuota bersama — terutama generate gambar AI dan media. Karena itu kuota per sekolah adalah fitur inti, bukan pelengkap yang dikerjakan belakangan.

10 Keputusan yang Masih Terbuka
